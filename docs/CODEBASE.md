# Yeet codebase structure

Yeet keeps orchestration code separate from policy, persistence, presentation, and external I/O. A source file should have one primary reason to change. When a module starts accumulating a second independent responsibility, move that responsibility into a named child module instead of extending the parent indefinitely.

New or extracted Rust modules should normally stay below 1,200 lines including focused tests. The central `agent.rs`, `Harness/service.rs`, and `tools.rs` coordinators are capped at 1,250 production lines; every Rust production module has a 1,700-line hard ceiling and every Rust source file has a 3,000-line absolute ceiling including tests. `RuntimeSource/src` TypeScript modules are capped at 1,200 lines. These limits are regression guards, not targets to fill. Tests should be colocated only while they remain small; large suites belong in a dedicated `tests` child module.

The Harness runtime is split by lifecycle responsibility. `Harness/service.rs` owns command routing and top-level service wiring. `Harness/service/run.rs` owns the top-level run lifecycle (admission, coordinator driving, event projection fencing, terminal settlement, post-run persistence and titling) and documents the single-executing-run invariant. `Harness/service/autonomy.rs` owns Manual/Goal/Autonomous policy and the per-cycle continuation decision. `Harness/service/replay.rs` validates and executes regenerate/edit-last. `Harness/service/persistence.rs` owns the two-phase session write (prepare under the live-state lock, commit after release). `Harness/service/state.rs` owns live session and streaming state. `Harness/service/events.rs` projects agent events into that state and into event-log records. `Harness/service/lifecycle.rs` owns session replacement, interruption, compaction, stuck-run recovery, and shutdown. `Harness/service/settings.rs` owns user-facing configuration commands, while `Harness/service/settings_support.rs` contains their pure adapters. `Harness/service/capabilities.rs` owns capability toggles. `Harness/service/debate_runtime.rs` runs debates and `Harness/service/debate_context.rs` grounds debate subjects in the workspace. `Harness/service/titles.rs` owns session-title generation. `Harness/service/transport.rs` owns harness-state envelopes and compact UI-facing tool activity details.

The agent is split between execution and policy. `agent.rs` owns the turn loop, rollover decisions, model response decisions and retry policy. `agent/request_assembly.rs` selects each attempt's tool surface and Jev policy, appends request overlays, builds metadata and cache diagnostics, and rejects same-window prefix rewrites before dispatch. `agent/tool_round.rs` owns guarded dispatch, parallel read-only MCP batch setup, cache-aware tool-result insertion, evidence and goal observations, workspace-write accounting, failure advice, and round progress/runaway bookkeeping. `agent/policy.rs` classifies requests and selects prompts/tools/history. `agent/runaway.rs` detects repeated tool loops. `agent/progress.rs` turns heterogeneous tool results into progress/failure signals. `agent/tool_protocol.rs` normalizes streaming and malformed tool-call formats. `agent/model_stream.rs` consumes one provider stream into a model attempt. `agent/cache.rs` owns prompt-cache boundaries and diagnostics. `agent/context.rs` and `agent/history.rs` own context persistence and history compaction.

The tool registry is likewise a coordinator rather than an implementation bucket. `tools.rs` owns registry state and routes each call to a domain executor. `tools/catalog.rs` (`ToolCatalog`) owns model-facing schemas, Skill/MCP/Worker/project-memory activation maps, read-only MCP annotations and capability toggles, and answers enablement and routing queries. `tools/context.rs` (`ToolExecutionContext`) owns the identity and authority every call runs under: workspace and session, working directory and context roots, hard access root, protected session-state paths, and approvals. `tools/external.rs` executes activated external tools. `tools/io.rs` implements workspace/web/document/data reads and Skill scripts. `tools/evidence.rs` (`ToolEvidence`) owns model-visible duplicate coverage, task edit snapshots/read coverage, web provenance, mutation validation, auxiliary usage and workspace generations. Its lifecycle distinguishes visibility reset, task cleanup and workspace invalidation. `tools/service_backends.rs` owns Foundation/web routing configuration (`ToolServiceConfiguration`) and semantic service adapters; configuration survives task cleanup. `tools/editing.rs` owns structured edits and delegates workspace evidence invalidation to `ToolEvidence`. `tools/shell_runtime.rs` owns shell routing, shell permits and bounded evaluator calls. `tools/session_tools.rs` owns artifact-store and session-catalog tools. `tools/definitions.rs` contains model-facing built-in schemas. `tools/support.rs` contains small stateless argument/schema/range helpers. `tools/paths.rs` owns path-boundary checks and workspace revision fingerprints.

`Harness/core.rs` holds provider-neutral model types; `Harness/core/provider_bridge.rs` is the ProviderBridge client for the Node sidecar. `Harness/session_store.rs` keeps the public store API and the semantic save/load path, with `Harness/session_store/objects.rs` (content-addressed components, manifest commit point), `events.rs` (append-only event log), `locking.rs`, `migration.rs` (legacy readers), `export.rs`, and `workspace.rs` (stable workspace identity). `background.rs` orchestrates the workspace daemon loop. `background/connection.rs` owns frontend attachment, compatible recovery, heartbeat liveness and session-affinity reconnect. `background/daemon_lifecycle.rs` owns endpoint identity, leases and startup/recovery locks; `background/protocol.rs` owns handshake compatibility. `background/session_runtime.rs` owns runtime construction, asynchronous retirement and interrupt/idle policy; `background/runtime_process.rs` owns the dedicated Harness thread and cached reconnect projection. `background/routing.rs` owns client routing and runtime state publication; `background/client_writer.rs` bounds asynchronous client delivery. Runtime topology and invariants are described in `docs/Basic Execution Structure.md`.

Maintainability comments follow the same rule as the module split: every new module gets a `//!` responsibility note, and non-obvious structs and methods get a short `///` contract explaining what they own or guarantee. Comments should explain responsibility or invariants rather than restating syntax.

Before merging structural work, run `Scripts/check.sh` (add `--install` on a fresh checkout to `npm ci` the JavaScript dependencies). It runs `cargo fmt --check`, `cargo check`, `cargo test --all-targets`, `cargo clippy --all-targets -- -D warnings`, the RuntimeSource build and Node tests, the web typecheck and a CLI smoke test, and reports each as PASS, FAIL (code), ENV (missing tool or dependency) or SKIP; exit status 1 means code failures and 2 means only environment gaps. The source-layout test is intentionally part of the Rust test suite so architectural regressions fail ordinary CI instead of relying on a separate manual checklist.
